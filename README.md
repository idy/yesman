## What makes a yesman different

- **A manager, not a coder.** The lead has no shell and never does the work itself. It only talks with you, plans and manages, so it is always free to answer.
- **It takes the whole job.** It turns your goal into tasks on a board and hands each to a worker, without waiting on any of them.
- **It manages upward, so you don't have to manage down.** Workers bring their questions, failures and reports to the lead, which answers them itself. Workers never interrupt you.
- **It does everything it can, and leaves you only the hard calls.** The decisions it cannot make reach you together, once everything else is done.
- **It works on a project, not a repository.** A yesman checks out worktrees of whichever repositories the project needs into its own workspace, one per worker, each on its own branch.
- **One pool of bare repositories.** Each repository is cloned once, written only by yesman, and shared by every yesman.
- **It picks up where it left off.** Shared Knowledge, task history, the board and every agent's session survive restarts.
- **Coming next: always on.** A yesman connected to a channel, talking with users and customers, turning what they need into tasks, and shipping release after release.

yesman is a tray app for hiring yesmen. A yesman takes on one project: it gets a workspace directory of its own, checks out whichever repositories the project needs from a shared repo pool, keeps notes its agents share, and starts workers when the job splits up. You talk to its lead in a Claude Code-style window.

> Status: early prototype. Hiring, the repo pool, worktrees, lead and worker agents, shared knowledge, and the window work on macOS. The app also compiles for Linux and Windows, but only macOS has been run. Watching pull requests is not built yet.

## How it works

| Piece | What it is |
| --- | --- |
| Repo pool | GitHub repositories, kept as bare repositories under `repos/` and written only by yesman. A repository is fetched whenever someone checks it out of the pool, and all of them with Fetch all, or every few minutes when Settings › Repositories says so. A fork also fetches the repository it was forked from, as its `upstream` remote. |
| Yesman | A workspace directory under `yesmen/<name>/`. Its worktrees, of any pool repositories, are checked out into it with `git worktree`, each on its own branch. |
| Lead | A [pi](https://pi.dev) agent in RPC mode, working in the workspace. You talk to it; it plans, keeps the board, Knowledge and Working log, and delegates. It never does the work itself, so it stays free to talk: it has no shell, and writes only these shared documents. It answers for its workers and sees the work through: it takes their questions and failures, decides what it can, and brings you only the decisions it cannot make, together, once everything else is done. |
| Workers | More pi agents in the same workspace, started by the lead for one task each, with a title naming its subject. The lead never waits for them: a worker's final message is sent to its lead when it finishes a run, and the lead is also told when a worker's run is stopped by you or its process fails. Once its report reaches the lead, a worker's process closes and it shows as done; a message to it starts it again with its session. |
| Knowledge | `.yesman/knowledge/`, durable development conventions, user preferences, architecture decisions and reusable pitfalls, listed in `INDEX.md`. The lead maintains it from worker discoveries; finishing a task alone does not justify a note. |
| Working Logs | `.yesman/task-log.md` is a short TOC linking to per-task/PR/release Markdown records in `.yesman/task-log/`. The lead maintains it from worker reports: brief date/title/link/result in the TOC; full refs, validation, release and recovery evidence in the related detail. History is read on demand, outside the Knowledge index. |
| Board | `.yesman/board.json`, the yesman's task list: each task has a status (todo, doing, blocked, done, dropped), an owner, and a note on where it stands. The lead adds tasks and hands them to workers; workers keep their own tasks current. It is the plan, not what the agents are doing now. |
| Topics | `.yesman/topics.json`, the user's questions and discussions worth finding again: each topic has a short summary, the conclusions the user confirmed, the questions still open and its sources. The lead keeps them with `yesman_topics`; the user creates and edits them in the Topics pane and sends messages about one from there. See [Topics](#topics). |
| Sessions | Each agent's pi session log in `.yesman/sessions/<agent>/`. Agents resume their latest session when they restart. |
| Secrets and variables | Environment variables every agent's commands get, edited in Settings: secrets in `secrets/secrets.sops.yaml`, encrypted, and variables in `variables.yaml`. |

By default agents run a project-managed, pinned [pi](https://pi.dev) runtime (1.5.2 with yesman's native queue patch), with your usual pi configuration (models, plugins, MCP servers), plus yesman's extension, [`pi/yesman.ts`](pi/yesman.ts). The first start prepares it in yesman's own cache using Node.js and npm; it does not modify your global pi installation. `YESMAN_PI` and custom PATH wrappers keep their original execution behavior. See [runtime distribution and compatibility](docs/native-queue-cancellation.md). Before each run the extension gives the agent its yesman's context: the workspace, its worktrees, the pool, the knowledge index and the other agents, and a lead the titles of its open topics. It also adds these tools, which call the app's loopback API:

- `yesman_repos`, `yesman_repo_add`, `yesman_checkout`, `yesman_worktree_remove`, `yesman_agents`, `yesman_board`, `yesman_env`
- for leads: `yesman_worker_start`, `yesman_worker_send`, `yesman_worker_answer`, `yesman_worker_remove`, `yesman_topics`

Agents register temporary checkouts with their purpose and board task. After saving completion and exact-head recovery evidence, reviewers reclaim their clean, unused detached trees; authors and release workers reclaim branch trees after the exact source PR is merged and their associated task finishes. The lead arranges a verified batch fallback for missed cleanup. Primary, active, dirty and unknown resources stay protected, while branches, refs and session history remain available. See [worktree completion and recovery](docs/worktree-cleanup.md) for the tool contract and safety boundaries.

For a lead, the extension also takes away pi's `bash` and adds the read-only `grep`, `find` and `ls`, and allows `edit` and `write` only under `.yesman/knowledge/`, for `.yesman/task-log.md`, or for flat Markdown records `.yesman/task-log/<name>.md`. Task-history targets must be ordinary unaliased files with ordinary parents; backups, nested directories, other metadata and linked paths are refused. These are pi tool-hook restrictions, not an OS sandbox. Code work still belongs to workers. Tools from your own pi configuration stay.

New workspaces start with a Knowledge index and a short Working log TOC with formatting/size guidance and a detail directory. Startup only fills missing paths, preserving empty/custom logs, notes, links and directory placeholders. Existing single-file logs stay readable; migration is an explicit offline operation with a dry-run, lossless originals/slices, hashes, resumption and rollback. See [workspace documents](docs/workspace-documents.md) and [legacy migration](docs/task-log-migration.md).

Only a lead turns to you. A question a worker's tools ask (an extension dialog) goes to its lead as a message, which answers it with `yesman_worker_answer`; the worker shows as asking its yesman, and you can still answer it from its conversation. A worker's failure goes to the lead too. When the lead ends a run with board tasks still to do or in progress and no worker running, yesman reminds it of them once, until you or a worker write to it again. You are notified when a lead asks you something, fails, or finishes with its whole yesman settled.

**Needs You**, at the top of the sidebar, gathers what waits on you across every yesman, with its count. It lists only structured requests, never anything guessed from what someone wrote, a board status or how a run ended:

- a lead's own question (an extension dialog: yes or no, a choice, or text);
- a worker's question its lead handed to you with `yesman_needs_you` `handOver`, because only you can answer it. Its other questions stay with the lead;
- a handoff the lead registered with `yesman_needs_you` `add`: a decision, information, logging in, installing, or another step only you can take, linked to its board task. Handoffs are kept in `.yesman/needs-you.json`.

Each request says what to do, where it is from, what kind it is and how long it has waited. Opening one selects its agent's conversation (a worker for a handed-over question, else the lead) and focuses the request there, keeping unsent drafts; a handoff can also find the lead's tool call that registered it in the folded work log, and **Back to Needs You** returns to it. A dialog leaves the list when it is answered, cancelled, stopped, removed, or when its timeout passes and pi answers it itself (a late answer is refused). You close a handoff with **Mark done** or **Not needed**; its lead hears which as a yesman notice, and **Mark done** on logging in, installing or a manual step is your own confirmation, which the lead checks before relying on it. The lead can resolve a handoff itself. Closed handoffs stay briefly as history (the 30 closed most recently) and never count; a tool call that registered a handoff never registers another while its yesman remembers it, even after it left the history or the app or lead restarted: the latest thousand such calls are kept as they are, older ones as a 64-bit fingerprint, the first 64 bits of a SHA-256 of the call. A fingerprint is not the call, so a new call whose fingerprint equals an older one's is refused as a repeat; with the memory full that happens about once in 7×10^13 new calls, and the lead calls again. A yesman remembers at most 262,144 tool calls, its kept handoffs' included. From 90% its lead hears so, and Needs You says so; once full, a new tool call is refused, saying why, while reading, closing, answering and handoffs without a call go on, and closing never needs more room. You then start a new memory from Needs You, after a confirmation: it forgets the fingerprints, never a handoff or the calls kept as they are, is recorded (the last eight, each with how many it forgot and a SHA-256 of them) and the lead hears of it. After a reset a forgotten call made again registers one handoff, which is then remembered again; each later reset can let it back once more. A confirmation shown before the memory changed or was reset meanwhile forgets nothing. A handoffs file from a pre-release version keeps what it remembered: its fixed-size filter still refuses the calls it holds, and, once nearly full, many new ones; a file whose older calls were forgotten without a trace refuses every new tool call. Needs You offers the same reset for either, and nothing is cleared until you confirm it; the reset forgets the calls such a file remembered, never fields a later version wrote beside them. The confirmation answers only the reset it was opened for: one that was cancelled, or replaced by another before it closed, forgets nothing, and when the reset finishes focus returns to the page only if you are still on it and have not moved focus elsewhere. Each yesman's handoffs file is read and written on its own: it must be a regular file in the workspace's own `.yesman`, in a workspace that is a folder of the data folder, never followed through a link, and a damaged, linked or oversized one is reported and left as it is, holding up no other yesman. Which yesman the workspace holds is read from its own `.yesman/yesman.json`, which must be a regular file of at most 1 MiB: a link, pipe or device in its place is refused without being waited on, and one that cannot be read or parsed is an error, not another yesman. Someone who edits the file while a change is being written keeps their edit, and the change fails; only an edit in the last instant before the file is replaced can be lost. Fields written by a later version are kept. Only the lead process running when a change commits can make it: a lead stopped or restarted meanwhile changes nothing. Handoffs move into the archive with their yesman, and a new yesman with the same name starts without them; a window opened before cannot close the new one's. Requests never carry passwords, keys or codes: the lead points you to Settings › Secrets. The lead's context lists only how many requests wait, with their titles; `yesman_needs_you` lists them in short or reads one in full. Requests above the composer take at most part of the window and scroll, a long detail within its request, so the conversation and the composer stay in view. The tray counts what waits, kept handoffs included, from startup.

The sidebar lists each yesman's lead with its workers under it. Active workers come first, followed by finished, stopped or failed workers; each set keeps the order they started. Right-click a yesman and choose **Rename…** to change its displayed name, including to a name with spaces or Chinese characters. The label is saved in `.yesman/yesman.json`; its original workspace name, directory and agent IDs stay the same, so its running agents, conversations and tools keep working. Displayed names do not have to be unique.

Each worker has one line with its status, a number such as a1, and the subject of its work in words, its title or else its board task's title, never the commands it runs. The board uses the same numbers, and hovering a worker shows its name. A working agent shows how long its run has gone on. A done worker stays listed, greyed; right-click the yesman to hide or show its done workers. What an agent is doing now, taken from its run's events, shows at the foot of its conversation while it works, and the lead sees it in its context.

Everywhere else in the window, right-click (Control-click on macOS, or Shift+F10 or the menu key) opens yesman's own menu: **Copy** for selected text, **Open Link** and **Copy Link** for a link, and **Cut**, **Copy**, **Paste** and **Select All** in a text field or the editor. The web view's menu, with Look Up, Translate, Search with Google, Share and Services, never shows. In the message box, **Paste** attaches clipboard images as ⌘/Ctrl+V does; elsewhere it pastes text only. The editor's Find box is a field of its own. On macOS a Control-click only opens the menu: it does not also open a link or send a message. Copy and Cut go through yesman's clipboard bridge and never copy a password or a secret's value; a right-click keeps a field's caret, selection and draft as they were, and ⌘/Ctrl+C, X, V and A work as before.

The Name field when hiring is a display name too: enter `GizMoth`, a name with spaces, or Chinese text directly. yesman preserves its spelling and assigns a safe lowercase internal workspace name (`GizMoth` uses `gizmoth`; another uses `gizmoth-2`). Labels do not have to be unique. Existing workspaces keep their original internal names and paths.

Workspace metadata in `.yesman/yesman.json` has a 1 MiB limit on its encoded JSON, including indentation, escaping and the final newline. Hire or Rename refuses output above that budget before publishing it; a failed Hire leaves no partial workspace. An existing oversized file stays untouched: the sidebar identifies that workspace as unavailable and shows the path, observed size and limit, while other workspaces remain usable. To repair it, quit yesman, back up the file, reduce its encoded size and preserve its original `hiredAt` field before reopening. No automatic truncation, migration or re-hiring occurs. Missing or malformed metadata keeps its existing fallback behavior; the size error is reported separately so it cannot silently change workspace generation.

The crew are the models yesman runs agents as, listed in Settings › yesman: each option is one of pi's models at one reasoning effort, such as Claude Opus 5.5 at high. A new yesman's lead runs as the option chosen there for new yesmen, recorded in its `yesman.json`, so hiring asks only for a name; a lead that resumes its session keeps the model it was using. The lead runs each worker as an option it names with `yesman_worker_start`'s `crew` parameter, or else as its own model and effort, which must be an option too; with no options, no yesman can be hired and no worker started.

The lead chooses by scores it sees in its context: [Artificial Analysis](https://artificialanalysis.ai)'s Intelligence Index, output speed, coding, and cost and time per task, for each option at its effort. Settings › yesman shows the same figures in each model's row, with their units; unmeasured figures are shown as a dash and the user's own scores are marked as estimates. They come from a snapshot of Artificial Analysis's leaderboard embedded in the app, [`internal/crew/scores/`](internal/crew/scores/), one row per model and effort, found by the model's name: pi's model ID or name, without where it is served (`codex-remote/codex/gpt-6.1-sol` and "GPT-6.1 Sol · Codex" both find GPT-6.1 Sol). A newer snapshot is a newer dated CSV file there with the same columns; the newest date wins. A score with no effort specified is used across efforts only when it is the model's single score with no named efforts, and the page marks that the source did not specify the effort. When Artificial Analysis has no record of a model at an effort, adding it asks for your own estimate, intelligence at least, on the same scales.

yesman reads pi's catalog by starting pi on its own once, when it is first needed, and again when you ask on the page after changing pi's configuration.

Settings › Model usage shows what agents actually used, apart from those benchmark scores: for each provider, full model ID and effort, the workers (or leads) that used it, the board tasks done with it, its responses, input, output, cache and total tokens, and its measured output speed. It reads the agents' pi session logs in the current yesmen, only as far as each file grew since the last read, and can show one yesman, workers, leads or both, and the last day, week or month. Each response counts under the model and effort pi recorded for that request, so switching models in a conversation splits it; a response without a recorded effort shows as Not recorded. A worker started again under its name is another worker, kept apart by when each started even after it is removed (yesman keeps worker starts in `.yesman/worker-starts.json` from this version on, the latest 10,000 of each yesman; earlier starts of a removed name, and those dropped, count as one, and the page says from when starts were dropped), and one that used several models is in each of their rows and once in the total; the owner of a task done in the period counts too. A done task counts for the model and effort of its owner's latest response that had ended when it was marked done (pi writes each response once it has ended; a response ending later never changes this): the board records that time and owner from this version on. An older task counts only when its owner used a single model and effort and no other worker held the owner's name since the task was created; edits such as a note never move a task. Where dropped starts leave which worker held the owner's name unknown, a task counts for no model. Reopened and dropped tasks do not count, nor does a worker finishing a run. Tokens are pi's own usage, including failed and stopped responses, cache warming, compaction and tools; input excludes cache reads and writes, the total includes them, and output includes reasoning. Output speed is output tokens per second of response time, from sending a request to its last token (pi's `durationMs`), over completed responses, weighted by their size; it is not Artificial Analysis's figure, and parallel agents do not add up to it. Costs are not shown: pi's are estimates from catalog prices. Logs are read only from inside each workspace: a linked `.yesman` leaves that yesman out, and linked sessions, agent directories or logs, and logs with other hard links, are skipped; the page names each. A log already read is read again only as far as it grew, and whole again when it was replaced by another file, did not grow, or changed where it was read up to. Dismissed yesmen and deleted logs are not included, and what pi did not record is not reconstructed.

A conversation reads as what you asked and what the agent told you. Your messages, with their images, and the agent's text stay in full, in order, including any question it puts to you. The work between replies (thinking, tool calls, board changes, starting workers, workers' reports and yesman's notices to the lead) folds into one line each time: while the agent works it says what it is doing, and afterwards whether those steps finished, stopped or failed, with how many thoughts, tool calls and reports they held. Open the line to read them in their original order; nothing is removed from the session or from what the model sees. The line speaks only for the steps in it: a lead's run that started a worker is not the worker's work done.

yesman tells your messages from its own by structure, never by their text. With the managed runtime, native occurrence identity and the exact recorded session entry bind each input to its origin without changing model messages; identical text/images stay distinct through queue promotion, history reload and compaction. Worker reports, questions, reminders and the lead's messages to its workers reach pi as ordinary prompts. On older supported runtimes, the app follows the records those runtimes expose, in order: an answer says whether a prompt started a run, was queued or was taken by an extension, and queue updates show the text after input hooks. Ambiguous or missing identity remains unknown. yesman's extension records that in pi's session as a separate entry beside the message (who, what kind, which worker, and for your messages their submission ID); pi's messages stay as they were, so neither the model nor other extensions' context and provider hooks see it, and the app adds it to the messages it shows, live and after a restart. When pi's records cannot tell, such as two queued messages with the same final text from different writers, or a message another extension queued, the message is shown as a person's, as it was written. So is history from before this was recorded: it is never rewritten, and later runs do not change how it reads. A message tied to its submission shows its delivery status lightly beneath it. A submission not in the conversation yet, such as one still sending, queued or refused, reads as your message with its status beneath it: exactly as this window sent it, text and images, while the window has it in memory, or else what its receipt keeps, a preview and the number of images. Receipts outlive their messages' place in the conversation, for those from before this was recorded or summarized away with earlier conversation. Those with nothing more to know fold into one line of earlier submissions at the end, opened to read what was kept of each. Confirmed native pending messages and failures from the current agent generation stay visible even when the window's eight-message display cache expires or another input is sent. A pending row can read complete originals from the existing bounded Go memory after a page reload; if those originals are gone, it honestly shows the retained preview and image count.

The composer lets you choose the current agent's model and reasoning effort from the right side below the input box, from any of pi's models, crew or not. Models come from pi's configured, authenticated catalog, grouped only when there is more than one provider; effort shows only the levels the selected model supports. Change them between runs without starting a new conversation. pi saves the selection in that agent's session once it has messages, and restores it when the agent resumes.

The composer accepts images from its **Attach images** button, pasted screenshots or images, and files dropped onto the input. It previews each attachment and lets you remove it before sending. PNG, JPEG, GIF and WebP are supported, up to four images, 5 MB each and 10 MB in total. Images travel with the message to pi, including messages sent during a run; you can send an image with or without text. Draft text and attachments stay with their agent while switching conversations, and remain available to retry if submission fails.

Messages have a **Copy message text** action that preserves raw text, Markdown and line breaks without changing the composer. Confirmed pending follow-ups also offer **Send now**: the same native entry moves to steering, retaining its identity, full payload and other messages' order. Steering waits for the next eligible input checkpoint after the current response and complete tool batch; it does not interrupt a model or tool in progress. Already-steering messages show that waiting state without a second acceleration button. During idle-session preparation, Stop leaves the original message and images in the native queue so they can still be recalled; a message already taken is recorded without being requeued. A reliably pending message also has **Cancel and edit**: it atomically leaves pi's queue and its complete original text and images return to that agent's input. Press **Up** in an empty composer with no attachments to recall the newest eligible message; its composer-only binding is listed in Settings › Shortcuts and can be changed there. The command palette, shortcut recording and input methods keep their own keys. Existing drafts are protected; edit and explicitly resend to create a new submission. Messages pi already took offer Copy only. Image-only inputs disable text copying, and a truncated historical receipt cannot stand in for original text. External pi runtimes without selective cancellation retain Copy and sending; the queue status explains that recall is unavailable. Original restore payloads are bounded in memory, so old history or a whole app restart cannot recreate lost attachments.

The context meter beside these choices opens pi's estimated current context usage and model limit, with free space, cumulative input/output and cache usage, and message/tool counts. It refreshes after messages, tool results and compaction. Current context and cumulative session totals are kept separate; when pi cannot report the current context size, such as just after compaction, the viewer shows it as unknown.

The app keeps running in the tray with its window closed. Agents are child processes of the app, so quitting it stops them; they resume from their sessions next time.

The files pane, opened from the titlebar, shows the workspace of the yesman you are talking to as a tree, and opens its files in tabs: text and code in an editor with syntax highlighting that saves with Cmd/Ctrl+S or by itself as you type, Markdown rendered, images shown. It follows changes as agents make them, and never saves over a file that changed on disk since it was opened without asking. Large files stay quick: the editor draws only the lines in view, and files over 5 MB open read-only at their first 512 KB. Each folder in the path above a file opens a list of that folder. Cmd/Ctrl+P (by default) goes to a file by name, and its menu checks out repositories, opens Knowledge or Working Logs and dismisses the yesman. Its edges can be dragged.

The info panel sits between the conversation and the files, and shows the yesman you are talking to at a glance; the titlebar hides or shows it. One card lists its entries, a row each, in this order: **Knowledge** (知识库 in Chinese), with its number of notes, and **Working Logs**, the task log, open their documents in the files pane, rendered and read-only; **Needs You**, with what waits on you from this yesman (or that its handoffs cannot be read, or that its lead cannot hand you new requests until you start a new memory), opens Needs You showing only this yesman's requests, with **Show every yesman** and **Back to the conversation**; a refresh keeps focus on either while the page still shows the same yesman, hired at the same time, and moves it to the heading once the control is gone. **Topics** (话题), with its number of open topics (or that its file cannot be read), opens the Topics pane beside the conversation. Working Logs starts with a short TOC; its links open individual detailed records, with Contents, anchors, browser history and reload. Storage folds into one row with the disk the workspace takes; open, it shows a bar of its largest parts (each worktree, the conversations, the knowledge, the rest of `.yesman`) and sums the others. Git's objects stay in the shared pool and are not counted. Worktrees lists the workspace's worktrees, each with the lines it changed against the remote's default branch, counting edits not committed yet and new files, or, when its branch is in a pull request, that pull request: its number, title, state, size and checks. Worktrees whose pull request is merged fold into one row at the end of the list, which opens them. yesman finds pull requests through the GitHub CLI, which also sees private repositories and checks, or else GitHub's public API, in the repository and, for a fork, in its upstream.

A worktree opens in the files pane, as its files or as its changes. The pane's bar is one row: the part of the workspace shown, whose menu switches to all of it, Knowledge, the working log or another worktree, then the path of what is open, each segment a menu of its folder; in Changes those menus hold only what changed. The changes tree arrives a folder at a time: the Go side measures the changes once and lists one folder per request, opening as many folders below it as 200 rows allow, so a diff of thousands of files never arrives whole. A file's diff is read when it is chosen, up to 256 KB unless you ask for all of it (16 MB at most), and drawn as it scrolls into view. The tree can also show folders alone: choosing a folder then lists its changed files, to see what changed without reading every diff, a thousand at a time.

The board, opened beside it in the titlebar, shows the same yesman's board as a list in the agents' order. Finished and dropped tasks fold into Done at the end, a blocked task shows why, a task's owner opens that agent's conversation, and a task expands to its detail and note. It follows the agents' changes; you change it by asking the lead. The board and the files share the place beside the conversation, one at a time.

### Topics

Topics keep what the conversation alone loses among workers' reports and other work: the questions and discussions worth finding again. A topic has a stable ID (`tp1`, `tp2`, …), a short title, a summary of what was asked or discussed, the **conclusions the user confirmed** kept apart from the **questions still open**, a status (open, resolved or archived) and its sources. Open **Topics** from the info panel or the titlebar: the pane lists them, newest change first, with a search over their text and a filter by status; a topic opens to read, edit, resolve, archive or restore. Archived topics stay, out of the way, and can be restored; nothing deletes one.

The lead keeps topics with `yesman_topics`, only for reusable explanations, important conclusions and open questions, not for every notification, report or tool result; a suggestion the user has not agreed to is never a conclusion. Its context lists the open topics by title only, and listing them with the tool gives titles and counts; it reads one when it matters. Agents see a topic's content and sources, not the app's records of the messages sent from it. Workers cannot change topics; the lead can cite their reports as sources. Task status stays on the board, history in Working Logs and rules in Knowledge: a topic cites them rather than copying them. Nothing reads old conversations to make topics.

Every change is made at the revision it was read at. A lead's change, like a board change, lands only while the lead process that asked for it still runs: one stopped or restarted, or whose yesman was dismissed and hired again, while its request was on its way changes nothing. When the user and the lead change a topic at once, nothing is overwritten: the lead reads it again, and the pane combines the parts only one side changed and leaves a part both changed to the user. Sources point to a message of the lead's conversation by its role and pi timestamp, a task, a Knowledge note, a link, a worker's reports or the conversation as a whole; a message no longer in the conversation's history, or matched by more than one, is said to be so and the conversation opens instead.

A topic's composer sends a message about it to the yesman's lead, into its one conversation, through the same submission receipts, retries and queue as the conversation's composer, with images too. The message begins with a visible line naming the topic, `[Topic tp3: title]`, shown before sending; the conversation shows it as a chip that opens the topic. The chip, and the topic's list of its messages, come from the app's record of what it sent from the topic, matched to the submission ID pi's own queue keeps with the message (its native input identity, the same one the conversation's receipts, Send now and Recall use), never from a message's text: the same line typed or pasted anywhere else names no topic, and a message whose origin is unknown belongs to none. Text beginning with `/` (pi commands, skills and templates) is sent as typed, without that line. Recalling a topic's queued message from the conversation puts it back in the conversation's message box as it was sent, line included; sent again from there, it is an ordinary message that names no topic. The topic records each submission before it is sent, but not which reply answered it: pi does not say, so replies stay in the conversation and the lead brings conclusions back to the topic. The file holds at most 300 topics in 4 MiB; one that cannot be read, is not a topics file yesman wrote, is larger, or is a link leading out of the workspace, is left as it is and reported.

Settings, at the foot of the sidebar, has thirteen pages: General (light, dark or the system's appearance, kept in `settings.json` in the data directory, and the language), Shortcuts (the keyboard shortcuts, below), Grant (the current application’s OS permissions, below), yesman (the crew, above, and what new yesmen run as, kept in `settings.json` too), Model usage (below), Repositories (the repo pool: name a GitHub user or organization to tick several of its repositories, or add one by `owner/repo`; they clone in the background, three at a time, and a clone that fails stays listed with its error until you try it again or dismiss it; Fetch all fetches the pool, and it can fetch by itself every 1 to 60 minutes), Secrets and Variables (the environment variables of agents' commands, below), GitHub App (the optional App identity for agent-created PRs), Storage (where yesman keeps its data, below), pi (pi's packages, below), Import and export (below), and About (the versions yesman runs with, and updates).

yesman is written in English and translated to Simplified Chinese. General › Language chooses one, or Match the system, the default, which shows the first of them among the languages of the system's settings, else English. The window, its menus, the tray and notifications change at once; MyGo keeps the choice (`App.SetLocale`): on macOS as the app's language in System Settings, which AppKit and WebKit also say their own texts in from the next launch, elsewhere in its `locale` file. The page translates itself in [`web/i18n.js`](web/i18n.js), with each message's English as its key in [`web/locales/zh-Hans.js`](web/locales/zh-Hans.js); Go translates its menus, tray, notifications and dialogs with `tr` in [`i18n.go`](i18n.go). A message without a translation shows in English.

The pi page manages [pi packages](https://pi.dev/packages): the extensions, skills, prompt templates and themes pi loads. It has three tabs. Info identifies the managed or external runtime, its version (or preparing/unknown state), a summary of the installed packages, pi's own settings file and what pi installs npm packages with (its `npmCommand` setting, npm unless set). Managed pi remains at this app's pinned version when global pi or shared packages are upgraded; use `YESMAN_PI` when a different host version is needed. Preparation belongs to the app, so closing a Settings request or stopping an agent only cancels that caller's wait. Old runtime directories under `<yesman-data>/.runtime/pi-managed/` are retained; there is no automatic cache cleanup. Runtime upgrades require regenerated lock/patch hashes and the complete [protocol acceptance checks](docs/native-queue-cancellation.md). Installed lists the packages pi's user settings install, with their version, source and what they provide; each can be updated, unless pinned to a version, or removed, and an npm package whose registry has a newer version says so. Browse searches the npm packages tagged `pi-package`, which is what pi's gallery lists, most popular first; a package's details show its README, links and preview, and install it. Install from source takes anything `pi install` does: `npm:name[@version]`, a git repository or URL, or a local path.

Packages are installed for the user, in pi's agent directory (`~/.pi/agent`, or `PI_CODING_AGENT_DIR`), so they load into every yesman agent and into pi wherever you run it. yesman changes them only by running `pi install`, `pi update` and `pi remove`, one at a time in the background; a change that fails stays listed with pi's or npm's error until you try it again or dismiss it. pi loads packages when it starts, so agents already running keep the packages they started with: the page says which, and puts the idle ones to sleep on request, to load the change when they next start.

### Keyboard shortcuts

The window has keyboard shortcuts for its common actions, a command palette, and Settings › Shortcuts to change them. They work while yesman's window has focus. There are no global shortcuts, and they need no Accessibility or Input Monitoring permission.

**Show all commands** (⌘K on macOS, Ctrl+K on Windows and Linux) opens the command palette. Search the window's actions, yesmen and workers by name, keyword or keys; ↑ and ↓ choose, Enter runs, and Esc or the same keys close it. Each action shows its keys. An action that cannot run now stays listed and says why. An action from the palette does what its button or menu does, with the same confirmations, on the agent shown. A dialog it opens, or a conversation it shows, keeps the focus.

| Action | macOS | Windows and Linux |
| --- | --- | --- |
| Show all commands | ⌘K, ⇧⌘P | Ctrl+K, Ctrl+Shift+P |
| Go to Settings | ⌘, | Ctrl+, |
| Open keyboard shortcuts | ⌘/ | Ctrl+/ |
| Hire a yesman… | ⌘N | Ctrl+N |
| Focus the message box | ⌘L | Ctrl+L |
| Stop the current run | ⌘. | Ctrl+. |
| Next / previous conversation | ⌥⌘↓ / ⌥⌘↑ | Ctrl+PgDn / Ctrl+PgUp |

These actions have no keys by default; they are in the palette and can be given keys in Settings: put this agent to sleep, go to this yesman's lead, go to the yesman that needs you, show Needs You, show or hide the topics, show or hide the info, open Knowledge, open Working Logs, check out a repository, rename this yesman, remove this worker, dismiss this yesman, add repositories, fetch all repositories, and open each Settings page. Some keys keep their jobs and cannot be changed: Enter sends a message or steers the run under way, Shift+Enter starts a new line, ⌘S (Ctrl+S) saves the open file, Esc closes a dialog, a menu or the palette, and Shift+F10 opens a sidebar entry's menu.

Keys are kept portably: `Mod` is ⌘ on macOS and Ctrl on Windows and Linux, so keys chosen on one computer mean the same on another. Ctrl (a Mac's Control key), Alt (Option on a Mac) and Shift are modifiers of their own. A key can be a letter, a digit, punctuation, F1–F24, an arrow, Page Up or Down, Home or End. Letters follow the keyboard layout's letter (on a non-Latin layout, the key's place), digits the number row, and punctuation the character it types. The Windows or Super key cannot be part of a shortcut.

What comes first:

- In a text field, the message box or the file editor, only shortcuts with ⌘ (Ctrl on Windows and Linux) or a function key work; other keys type. Keys the editor or the message box use themselves stay theirs, such as the editor's ⌘/ (Ctrl+/), which comments a line.
- An open dialog, menu or list, and the palette itself, keep every key. While an input method composes, and for the characters AltGr or Option type, keys stay text.
- A shortcut whose action cannot run now, such as Stop with nothing running, is left to the page and the system; only a shortcut that runs is taken from them. Held down, a shortcut runs once, except next and previous conversation, which repeat.
- Esc never stops a run.

Settings › Shortcuts lists every action with its keys, searchable by name or by keys. **Add** records new keys: the field shows the keys as you hold them, Esc cancels, and recording never runs the action. It refuses, and says why, keys that type text, move the caret or edit (copy, paste, cut, undo, select all), keys the system or yesman's menus take (such as ⌘Q, ⌘W, ⌘H, ⌘M and ⌘R on macOS, Alt+F4 and F10 on Windows), AltGr's characters and an input method's keys. Keys another action has can be moved to this one in a single change. An action has up to four keys: remove one with its ×, remove them all to turn the action's keys off, reset one action to its defaults, or reset all after confirming. The page also notes keys an AltGr keyboard may type with, and keys the file editor uses. Changes are saved at once, one after another, and kept across restarts: a change made while another is saving builds on it, and one that fails leaves the keys as last saved, with the reason on its action. The titlebar's buttons and the files menu show the keys in use.

Changed keys are kept in `settings.json` as `shortcuts`, by stable action ID, and only those that differ from the defaults (`[]` for none). Saving other settings keeps them, and action IDs this version does not know are kept for a version that does. Keys a computer cannot use, such as ones carried from another platform, show in Settings with the reason and do not run.

### Secrets and variables

Secrets (API keys, tokens) and variables (an account name, a region, an endpoint) are environment variables that every command of every agent gets. Each has a name, which is the variable's, a value, and a description that tells agents what it is for. Settings › Secrets and Settings › Variables edit them as a form, or as YAML with the editor; switching converts between the two, and a mistake in the YAML keeps it open there. A name is set in one of them only, and a secret's must not end in `_unencrypted`, which sops keeps in the clear. Comments in the YAML are not kept.

```yaml
version: 1
secrets:            # variables: in variables.yaml
  GH_TOKEN:
    description: GitHub token for idy; gh and git push read it
    value: ghp_…
  OPENAI_API_KEY: sk-…   # a value alone is short for one without a description
```

Secrets are kept in `secrets/secrets.sops.yaml` in the data directory, a [sops](https://getsops.io) file: names in the clear, every value and description encrypted with AES-256-GCM, a MAC over all of them, and the data key encrypted to an [age](https://age-encryption.org) key. The key is `secrets/identity.age`, encrypted with a password. Setting up makes the password at random and keeps it in the system's credential store (the login Keychain on macOS, the Credential Manager on Windows, the Secret Service on Linux), keyed by the vault's age recipient, so yesman unlocks the secrets when it starts; Settings › Secrets copies it. Where the system has no credential store, you choose the password and type it after each launch. Unlocking reads the key into memory until you lock again or quit yesman; while locked, commands run without the secrets. yesman reads and writes the sops format itself, so neither sops nor its key services are needed; with the age key, which `age -d secrets/identity.age` gives with the password, `SOPS_AGE_KEY_FILE=key.txt sops edit secrets/secrets.sops.yaml` edits the same file, and yesman keeps any other age recipient sops added. A lost password cannot be recovered: the exported configuration keeps a copy. Variables are kept in plain text in `variables.yaml`, which you may edit by hand.

Agents get them through yesman's extension. Its `bash` tool (and `powershell` on Windows) replaces pi's own and asks the app, before each command, for the variables and, while unlocked, the secrets, and sets them in that command alone: a change reaches the next command without restarting anyone, and pi's process, its other extensions and its MCP servers never see the secrets. The context says one sentence about them, and `yesman_env` says what each variable is: its description, a variable's value, never a secret's. Whatever a tool returns, output or a file read, shows a secret's value, or a line of one, as `[secret NAME]`, for values of six characters or more, including values the agent was given before they changed or were removed. This keeps values out of the model's context and the session logs; it does not stop a command from using a secret as it likes, or a determined agent from encoding one.

Neither page has a backup of its own: Settings › Import and export backs both up with the rest of the configuration, below.

### GitHub App identity

Settings › GitHub App registers or imports your own GitHub App and keeps its key in a separate encrypted vault, with the password in the system credential store. Select explicit workspaces and `owner/repo` names, save and test the scope, then enable it. Their agents' next `gh pr create` uses the App's bot name and avatar, including when a personal `GH_TOKEN` is configured. Other gh commands and Git pushes keep their existing credentials; a locked key or uninstalled repository fails without personal fallback. Private keys and installation tokens never enter pi, the model, the webview or the shell environment, and are not bundled in releases or normal configuration exports.

Use an already-pushed branch and explicit `--repo`, `--head`, `--base`, `--title` and `--body` or `--body-file`; `--draft` is supported. The App needs Pull requests write, Contents read and default Metadata read, with webhooks disabled. See [setup, identity boundaries and verification](docs/github-app.md) for the registration flow, supported commands, key storage and actual Bot-author test.

### Import and export

Import and export saves yesman's configuration as a TOML file, to back it up or carry it to another computer: the appearance, the fetch schedule, the pool's GitHub repositories as `owner/repo`, the variables, and the secrets: the vault's key file and secrets file as they are, encrypted, with the password from the credential store. With the password in it the file opens the secrets, so it is written readable only by you; keep it private. Importing its secrets where none are set up sets them up as they are and keeps the password in the credential store; where there are secrets, the file's are opened with its password and merged or replaced into them. A name both variables and secrets would set stops the import before anything changes. A file without variables or secrets, such as one of version 1, leaves those here alone, replacing too. The file also carries the keyboard shortcuts changed from their defaults, as `[shortcuts]`: merging takes the file's keys for the actions it lists and keeps the rest, and replacing makes the file's list the whole set of changes, so the other actions return to their defaults. A file without `[shortcuts]` leaves the shortcuts alone, replacing too. Workspaces, their knowledge and conversations stay out, as does where yesman keeps its data. Importing a file first shows what it would change, then either merges it, which clones the repositories it lists that the pool lacks and changes the settings it sets, or replaces with it, which also resets the settings it leaves out and removes the pool repositories it does not list. Replace keeps a repository that work depends on, one with a worktree checked out of it (in a workspace or the archive) or a branch with commits no remote has, and says why. It also stops the clones of repositories the file leaves out, except one an agent is waiting for.

```toml
version = 2
appearance = "dark"   # system, light or dark
auto_fetch = 15       # minutes: 0, 1, 5, 15 or 60
repos = ["idy/yesman", "idy/magpie"]

[[variables]]
name = "DEPLOY_REGION"
value = "eu-west-1"
description = "AWS region the deploy scripts use"

[shortcuts]           # keys changed from their defaults; Mod is ⌘ on macOS, Ctrl elsewhere
"pane.info" = ["Mod+Alt+E"]
"palette.open" = ["Mod+K"]
"agent.sleep" = []

[secrets]
password = "…"        # from the credential store
key = '''
-----BEGIN AGE ENCRYPTED FILE-----
…
'''
file = '''
secrets:
    GH_TOKEN:
        description: ENC[AES256_GCM,…]
        value: ENC[AES256_GCM,…]
sops:
    …
'''
```

In Settings › Storage, **Change…** lets you enter or browse to a data folder, then **Use folder and restart** opens it after restarting. Existing folders with data are accepted; a new folder starts fresh. To keep existing data elsewhere, quit yesman, copy the folder yourself, then reopen yesman and select the copy. Data transfers and any Git worktree path repairs are manual. The chosen location is kept in `yesman/storage.json` under the operating system's user configuration directory (Application Support on macOS, `$XDG_CONFIG_HOME` or `~/.config` on Linux, `%AppData%` on Windows). A launch with `YESMAN_HOME` overrides that choice. Below it, Usage measures the data folder in the background: its total size and file count, a bar of the repo pool, workspaces, archive, runtime files and the rest, each with its share, and the space left on its disk. A measure is reused for a minute unless you measure again; symbolic links are not followed. Storage also has a compact list of the repo pool, workspace parent, archive, secrets, variables, runtime files, settings file and storage configuration, with a Reveal action for each and the full path on hover.

Release builds update themselves through MyGo's updater: they check GitHub releases of `idy/yesman` at launch and every 6 hours, and download and install a newer version in the background. The titlebar then offers to restart into it, and the next launch runs it anyway. Only release builds, made with `mygo build` and signed, do that; development builds (`go run`, `go build`) never check.

**Restart and continue** (Settings › About, the command palette, or the tray's **Restart Yes Man**) restarts the app, and **Restart to update** goes the same way. A restart installs nothing by itself: it starts what is installed, so an update already downloaded and installed starts with it, as at any next launch. As the old instance quits, before its agents stop, it closes them to new starts and to new deliveries of workers' reports, and records in the data folder's `restart/` which agents it cuts short: those running a turn, workers waiting on a question to their lead or whose report to the lead had not been settled, and agents waiting for you (only to say so). That first record is provisional and lets no agent go on. Once the agents have stopped, it waits up to 5 seconds for reports under way and writes the record again, final, with where each got: not sent, taken by the lead's pi, or sent with no answer; a worker whose run finished in between is recorded for its report, not as working. If the final record cannot be written (too large, or a write error) or the app ends before it, the provisional one stays, and the next instance continues no agent: About says the record was not finished and how many interrupted agents wait for a message. It keeps the agents' workspace and agent identities, the reason and, for a report, its state and the SHA-256 of the worker's final message, never credentials, messages or session text. The next instance claims a final record once and checks each agent against its workspace: one archived, hired again, removed, replaced by a new worker of the same name, finished or put to sleep is left alone, and one you or its lead talked to first goes on with that. Each other agent starts from its session and gets one short yesman note to continue its work from its session and the board, checking whether an action with outside effects already took effect before repeating it. A report known not sent is handed to the lead once, read from the worker's session with no new run, and only if that final message is still the one recorded. A report the lead's pi had taken is not sent again and the worker is recorded finished, as it would have been; taken is not read, so the lead may not have read it before the restart. A report sent with no answer may or may not have arrived: it is not sent again, nor the worker recorded finished, and About shows it as uncertain, for you to ask the worker or the lead. All of a restart's agents share one 3-minute deadline, at most 4 at a time: an agent not started and admitted by then is sent nothing, and its own start is stopped. A note sent but not yet answered by then is shown as uncertain. Your messages and images are never sent again: messages still queued at the restart stay as interrupted submissions to send again yourself. Agents you put to sleep, stopped or that wait for your answer stay as they are. About shows what the last restart came to, counting every agent it recorded under what became of it. A plain Quit records nothing, and starting the app never wakes agents on its own; a record older than 15 minutes, damaged, not one complete JSON document, with a key twice, of another version or not a regular file is set aside unread and wakes nobody. A record holds at most 256 agents in 64 KiB, written compactly; one that would not fit is refused whole, never cut short. A restart cannot resume a command at the point it was cut, unsaved editor changes, or effects outside the app exactly once; updating from a version without this feature resumes nothing.

## Requirements

- Go 1.27 or later, and git; macOS 13 or later for the macOS app
- Optionally the [GitHub CLI](https://cli.github.com) (`gh`), signed in. yesman asks it which repository a fork came from and which repositories an owner has, private ones too, and clones `owner/repo` over the protocol it is set to use. - Node.js 22.19 or later, with npm and network access for the first preparation of yesman's managed pi runtime. A verified cached runtime subsequently needs only Node. Configure your pi models as usual. An explicitly selected external `YESMAN_PI` remains supported for sending; per-message recall requires its compatible queue capability.

## Test


The delivery check uses your installed pi with isolated configuration and a local deterministic provider, without calling a real model:

```bash
node scripts/check-delivery-pi.mjs
YESMAN_TEST_PI_FIXTURE=1 go test ./internal/server -run 'Origin.*PiFixture'
```

The origin checks run your installed pi through the app's own agents and API with a local pi-messages backend. They check who wrote each user message, live and after a restart, including when another extension's input hook rewrites your message into the text of a queued worker report. They also check that a context hook which serializes the history never sees or sends an origin, and that tool results replaced by an extension are recorded as final.

Submission receipts retain metadata only: a 512-byte text preview, image count, bounded error/session fields, and a private payload fingerprint. Each agent keeps at most 256 records in a 2 MiB file, with at most 64 active submissions. Terminal records expire after 24 hours on access. Pending records remain until a real status boundary; reaching the active limit rejects new submissions without changing pi's queue. Timestamped IDs and a persisted eviction watermark reject unknown expired/evicted retries rather than dispatch them again. Initial registration is durable before RPC dispatch; later states use one coalescing background writer per agent. Workspace use remains leased through initialization and durable registration, then releases before the RPC wait. Dismissal stops processes, seals final receipt state, and joins every writer before renaming; failed drains leave the original workspace in place. Same-name hires use a fresh generation, and old callbacks cannot restart or write into it. Legacy image-bearing files are compacted outside the manager lock, with a 32 MiB migration read limit that fails closed without overwriting an oversized file.

To drive the real window, build with the `e2e` tag and attach [`mygo-automation`](https://github.com/egoist/mygo/tree/main/plugins/automation):

```bash
go build -tags e2e -o /tmp/yesman . && YESMAN_HOME=/tmp/yesman-home MYGO_AUTOMATION=/tmp/yesman.sock /tmp/yesman
```

Automation cannot reach native file dialogs, so in such builds `YESMAN_E2E_SAVE` and `YESMAN_E2E_OPEN` name the files that Export and Import use instead of asking. `YESMAN_E2E_NAME` names the app otherwise, so that a test build runs beside another yesman instead of handing over to it.

## Release

`mygo.json` describes the app for the packaging adapter: its display name, stable slug, identifier, version, and update source. The main executable is `Yes Man` (`Yes Man.exe` on Windows); `yesman` stays available as a compatibility entry. See [application naming and packaging](docs/application-name.md) for installation and update compatibility. When changing the managed pi dependency, regenerate its lockfile and source patch hashes and complete the native protocol/SDK/Manager/browser acceptance checks in [the runtime maintenance guide](docs/native-queue-cancellation.md). Do not move the runtime to npm/latest or remove older cache directories as part of an app update; running processes may still use them.

To release a version:

1. Set `version` in `mygo.json` and add its section to `CHANGELOG.md`, which installed copies show as the release notes.
2. Merge that, then push the tag matching the next allocated `0.1.x` patch (for example, `git tag v0.1.30 && git push origin v0.1.30`).
3. [`.github/workflows/release.yml`](.github/workflows/release.yml) builds macOS, Windows and Linux and uploads them, with their signed updates, to a draft release.
4. Look the draft over and publish it. Installed copies then update to it.

Updates are signed with a key whose secret half is the repository's `MYGO_UPDATER_PRIVATE_KEY` secret, with a copy kept outside the repository. Installed copies accept only updates signed with it, so it must not be lost or replaced.

To build a release locally, without uploading: `go tool mygo build`, with the key in `MYGO_UPDATER_PRIVATE_KEY` for the update files. The repository's `mygo` tool routes builds through `tools/package`, which stages the pinned MyGo dependency in a temporary directory, applies the reviewed naming adapter, then invokes its ordinary builder. Other MyGo commands forward to the pinned upstream tool. The repository and module cache are unchanged; plain `go build` remains available for development. On macOS, enable the app-owned native permission bridge with `CGO_ENABLED=1 CGO_CFLAGS='-O2 -g -mmacosx-version-min=13.0' MACOSX_DEPLOYMENT_TARGET=13.0 go tool mygo build`; the release workflow sets these automatically.

The builds are not yet signed for other machines: macOS apps are signed ad hoc, which Gatekeeper blocks on first open from a download, and Windows apps have no signature, so SmartScreen warns.
