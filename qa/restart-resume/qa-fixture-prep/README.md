# t199 stateful package fixture prototype

**Reviewer-ready fragments; not an executed native acceptance run.** Scope is one isolated hosted macOS ARM64 S→private Q episode, one eligible interrupted agent and a persisted pause control. The default small seed is an active lead plus a second workspace's paused lead. An already-seeded worker can occupy the eligible slot without a new worker protocol. No actual S/Q input is selected or allocated.

This round implements the preparatory code authorized by the Lead. It does not reopen the original nine-payload packet, take over t198 or authorize package execution/publication. The Lead's narrowed scope supersedes the earlier plan's proposed full stateful platform duplication and environment-free profile migration: **neither is a new shipping requirement**. Keep ordinary restart/Quit CI, existing updater/install/platform regression evidence and actual downloaded dual-Mac/package validation by identity. Existing install rollback remains distinct from this deliberately failed-launch/explicit-recovery episode.

## Deterministic failed launch without a product hook

The pinned helper waits for S's PID to exit, moves the entire staged bundle to the installation path, restores the old bundle only if that move fails, deletes its work directory, then execs `/usr/bin/open`. It does not validate/repair the main executable during that move and has no launch-health rollback.

After the real updater has verified and staged Q and reached Ready, the sole fixture controller moves **only** staged `yesman.app/Contents/MacOS/Yes Man` to `.t199-held-main-<run>` in the same MacOS directory. `obstruction_plan` requires the existing `.yesman.app.update-*/app/yesman.app` layout, regular unique file, original SHA/size/mode and unoccupied hold name. `arm` additionally requires hosted ARM64, RUNNER_TEMP containment, unchanged plan/file identity and readback. Original bytes and permissions are not edited.

This happens **before** RestartToUpdate, so there is no race against final publication or launch: the intended main stays absent for the entire checkpoint→quit→bundle-move→open interval. The compatibility entry is a symlink to that same absent main. Moving the whole bundle carries the held file into installed Q, outside the deleted helper work directory. This is a deliberate fixture fault after signature verification, not a replacement trusted artifact or an install-move failure.

The later native run must prove all of the following before recovery:

- Arm receipt precedes the single actual restart request; S exited normally and the helper terminated.
- Actual OS/Launch Services failure is retained from the helper/initial log; no Q main PID or Q bridge appeared. A timeout by itself is insufficient.
- The on-disk record is **final**, from S to Q, with its original ID/raw bytes/hash and no claim; it remains unchanged until recovery. Provisional, expired, missing or already-claimed records fail this scenario.
- `recover` restores only the held file with the same inode/dev/hash/mode into the empty expected path. The outer adapter rechecks the complete installed Q inventory and strict code signature, then explicitly opens verified Q within15 minutes. It launches nothing automatically from this library.
- Q's completed last result binds the captured final ID/from/to/running version, exactly the declared eligible resumed set, one original user entry and one restart entry in the same real pi session. The provider's continued request must contain the old synthetic marker once. Paused agents receive no continuation; the next reopen has no new restart/provider request.

The obstruction is realistic for the inspected helper and needs no production hook in this design. **Its actual macOS Launch Services behavior is still unexecuted.** If the final helper/layout differs, `validate_contract` refuses: revisit the narrow controller adapter rather than guessing or racing launch. If hosted stderr/PID evidence cannot establish a failed launch, keep that cell unproven; the smallest fallback design is a fixture-only helper-observation barrier after final publication/before open, reviewed separately. No product hook or auto-rollback implementation is included.

For an unobstructed positive hop the transient final/claim files can be too short-lived for a filesystem watcher. Its observable proof is last.json plus same-session/one-note/no-replay counts and reviewed claim code, not a claimed count of rename syscalls. The obstructed recovery hop additionally binds the real stable final bytes to that completed result. No polling race is represented as exact syscall capture, and no power-loss or external-effect exactly-once claim is made.
