# macOS Developer ID signing and notarization

Release builds of yesman for macOS can be signed with the owner's **Developer ID Application** certificate and notarized by Apple. Configuration is optional. Until it is set, releases stay signed ad hoc, exactly as before.

Signing gives every release the same publisher identity: Apple's anchor, the Developer ID Application certificate type, the team's Team ID and the identifier `dev.idy.yesman`. That identity is what macOS can use to recognize later versions as the same app. Notarization lets Gatekeeper open a downloaded copy without warnings. Neither changes the updater: the Ed25519 key in `mygo.json` `updates.publicKey` still authenticates every archive and delta, and stays unchanged.

## Modes

The source decides. `packaging/macos/signing.json` holds `{"teamId": ""}` or the team's 10-character Team ID; the tag's own copy of it says how that release is signed and checked.

| Configuration | Release macOS job |
| --- | --- |
| No `teamId` and none of the four secrets below | Ad hoc, as before |
| A `teamId` and all four secrets, valid | `-sign <certificate SHA-1>`; MyGo signs each app with the hardened runtime and a secure timestamp, signs and notarizes each disk image and staples both, then writes the update archives, deltas, checksums and manifests |
| Only some of them, or any check failing | The job fails. It never falls back to ad hoc |

The tracked `mygo.json` stays the ad-hoc configuration: a plain `go tool mygo build` needs no flag or input. Only the release launcher, given a keychain that setup prepared, adds `macos.notarize` to a derived configuration (below).

The secrets, under the repository's **Settings › Secrets and variables › Actions › Secrets**:

| Name | Value |
| --- | --- |
| `MACOS_SIGNING_CERTIFICATE_P12` | Base64 of a `.p12` holding only the **Developer ID Application** certificate and its private key |
| `MACOS_SIGNING_CERTIFICATE_PASSWORD` | The password chosen when exporting that `.p12` |
| `MACOS_NOTARY_APPLE_ID` | The Apple Account email of the membership |
| `MACOS_NOTARY_PASSWORD` | An app-specific password made for this at account.apple.com |

The Team ID is public (it appears in every signature) and is committed, not a repository variable, so that a variable changed later cannot change how an already built release is judged.

A free Xcode “Personal Team”, an Apple Development, Mac App Distribution or Developer ID Installer certificate cannot be used: setup rejects them. App Store Connect *individual* API keys cannot use notarytool, so notarization uses the Apple Account with an app-specific password.

## What the release job does

1. **Prepare macOS signing** (`scripts/macos_signing.py setup`) is the only step that receives the four secrets. It refuses to run anywhere but a GitHub-hosted runner, because it changes the account's keychain search list. It makes a fresh directory of its own under `RUNNER_TEMP` (`0700`) with a `0600` receipt holding a random nonce, and writes the directory's path, device, inode and nonce as the step output `state` before creating anything else (if that write fails, setup removes the directory itself). In that directory it creates a keychain with a random password, writes the `.p12` to a `0600` file, imports it and deletes the file. The key's access list names `/usr/bin/codesign` (`-T`), and its partition list `apple-tool:,apple:,codesign:` lets Apple-signed tools and codesign use it without a prompt; the keychain goes first in the search list, where MyGo's `codesign` finds it. Setup then requires exactly one identity, valid on the runner, named `Developer ID Application: … (<Team ID>)`, signs a scratch file with it as MyGo will, and has `codesign` evaluate Apple's Developer ID Application requirement for that team. Last, it stores the notary profile `yesman-release-notary` in the same keychain. Its other outputs are the mode, the certificate's SHA-1, the team and the certificate name; none is secret. They are written last, inside setup's cleanup scope: if that write fails, setup removes the keychain and fails.
2. **Build and upload** runs `scripts/release_build.py` on every row. It receives no Apple secret; see below for the updater key and upload token. In Developer ID mode it first checks that `state` still names the directory setup made and its keychain, then builds with `-sign <SHA-1>` and the derived configuration's `macos.notarize` naming that keychain. MyGo builds the two architectures one after the other and uploads only after both: a signing, notarization (anything but `Accepted`) or stapling failure stops it before it writes that architecture's update files and before this build's upload. An architecture finished earlier may already have local update files, which are not uploaded. The other platforms' jobs are independent.
3. **Remove the signing keychain** always runs, given `state`. It opens the directory once (no link followed) relative to `RUNNER_TEMP` and keeps that descriptor: the directory must be the same device and inode, owned by the runner's user, closed to others, and hold a receipt with the same nonce. The receipt is opened without blocking or following links, and only a small regular file of the runner's user, closed to others and with one link, is read, with a bound; a FIFO, device, link or oversized receipt is refused at once. (What is read is the file that descriptor opened; renaming another file to the receipt's name afterwards does not change it.) The step removes the keychain's entry from the user search list (`security list-keychains -s`, which only rewrites the list of paths), then deletes the keychain file and the rest of the directory through the held descriptor, not by path, and removes the directory entry only while `RUNNER_TEMP` still names that directory, with `rmdir`. It does not run `security delete-keychain`: that tool opens the keychain by its path when it runs, so it would delete whatever keychain the path named by then. The keychain's unlocked state in `securityd` is only reachable by that path, which no longer exists, and ends with the VM. A directory replaced during cleanup is left alone and the step fails; the original is emptied where it was moved. A directory that holds a `retained.json` (below) is left as it is while the process groups it names have members, or their members cannot be listed. Without a `state` (ad hoc, or setup refused before making anything) it does nothing.
4. **Verify the Developer ID signatures and notarization** then checks both architectures' app and disk image: not ad hoc, the expected team and certificate, Apple's Developer ID requirement, hardened runtime, secure timestamp, a valid stapled ticket and Gatekeeper's “Notarized Developer ID” verdict. Each app's designated requirement must be, as `csreq` compiles it, exactly the Developer ID requirement of the team and identifier (an `always` or team-less requirement fails even when both architectures agree), and each app must satisfy the other's. The evidence is kept as the run's `macos-signing` artifact.

MyGo uploads within step 2. A signing, notarization or stapling failure stops it before that architecture's update files are written and before this build uploads anything; a failure of the final check in step 4 (designated requirement, Gatekeeper, ticket) happens after the upload. Any failed job means the draft must not be published; per the release policy, the tag is not moved or reused.

The draft gate `.github/workflows/macos-draft-smoke.yml` checks out the tag's source and reads its `packaging/macos/signing.json`, with no variable or secret. With a Team ID, the downloaded archives must pass the same signature, requirement, ticket and Gatekeeper checks before their startup runs; without one, they must be signed ad hoc. Tags made before this support carry neither file and keep the earlier check.

### Interruption and limits

- Every tool that setup, cleanup or the launcher starts (`security`, `codesign`, `xcrun`, and `go tool mygo` with everything it starts) runs as the leader of a process group of its own. When the tool exits, times out or the script is interrupted, the processes still in that group are sent `SIGTERM`, then `SIGKILL`, and waited for, before files are removed; the leader is not reaped until then, so its group ID cannot be reused by another process meanwhile. Only that group is signalled. If a process cannot be stopped, or the group's members cannot be listed, the step fails naming it instead of claiming it ended.
- In that case nothing such a process may still use is deleted. The leader stays unreaped, so the group ID stays the script's until it exits, and from then on that run deletes no private file. Setup keeps the `.p12`, keychain and directory; the launcher keeps its key, token and derived configuration directories. Each kept directory gets a `0600` `retained.json` naming the process groups. The always-run cleanup step then removes the signing directory only once every group it names is confirmed empty by a process listing; while one has members, or the listing fails, it fails and removes nothing. It never signals those groups, which no longer belong to it. A group ID is not reused while any member lives; if one is reused after they have all gone, the new members make cleanup refuse, which is safe. The launcher's directories stay on the disposable runner, or `python3 scripts/release_build.py --remove-retained DIR…` removes them under the same condition.
- Setup turns `SIGTERM`, `SIGINT` and `SIGHUP` (a cancelled job) into a failure, and on any other failure, once its tools' groups are confirmed stopped, removes its `.p12`, keychain, search-list entry and directory before exiting. Further signals are held until that cleanup has run. Each tool it starts must finish within 300 seconds, or setup fails and cleans up the same way. Only the last 64 KiB of each tool's output is kept in memory; it is redacted, and only its last six lines are shown in an error.
- Not covered: `SIGKILL` of the script itself, the runner going away, and descendants that leave their process group (a new session or group). After a `SIGKILL` the always-run cleanup step removes what setup left, provided the runner recorded setup's `state` output; otherwise the keychain stays on the runner until GitHub discards the VM with the job. Nothing here claims more than that.
- The nonce is a handoff token between the steps of one job, not a sandbox: a process of the same user can read or forge the state and receipt. The checks stop cleanup from deleting anything but the directory setup made and its contents, including when that directory or its keychain is replaced while cleanup runs; no tool deletes by path. The one remaining window is between the last path check and `rmdir`: a same-user process could swap in an empty directory at that exact path, which `rmdir` would remove (it cannot remove one that holds anything). Replacing the path with another keychain only drops that path from the search list.
- Only GitHub-hosted runners are used: a self-hosted runner would keep a killed job's files, so setup refuses one.

### Credential boundaries

- The four Apple secrets exist only in the setup step's environment. Setup gives every tool an environment without them (and without any name containing `TOKEN`, `SECRET`, `PASSWORD`, `PRIVATE`, `CREDENTIAL` or `P12`), refuses to start if one of their values is found under another name, never prints them, and never writes them to step outputs, `GITHUB_ENV`, artifacts or the workspace. It reports failures without argument lists and redacts secret values from tool output.
- Two tools take a secret only as an argument: `security import -P` (the `.p12` password, for an instant) and `notarytool store-credentials --password` (the app-specific password, while Apple validates it). Another process of the same user on the runner could read those arguments while they run; on a GitHub-hosted runner the VM and its single job are disposable. GitHub masks both values in logs.
- The build step has the updater key `MYGO_UPDATER_PRIVATE_KEY` and the upload token `GH_TOKEN`. MyGo starts go, the compilers, cgo's clang, codesign, xcrun, hdiutil, makensis and gh with its own environment, so `scripts/release_build.py` takes both out of it. The key goes to a `0600` file in a fresh `0700` directory, which the derived configuration names as `updates.privateKey`: only MyGo reads it, to sign the update archives, deltas and manifests. The token goes to a `0600` file there, which a `gh` wrapper first on MyGo's `PATH` reads before running the real `gh`. Every other child gets the step environment without any credential name, and the launcher refuses to start if a credential's value remains under another name. The files are readable by the runner's user while the step runs and are deleted when it ends.
- The derived configuration lives in a fresh directory under the ignored `build/`. It is `mygo.json` with its paths made absolute, `resources/` linked, the changelog and key file named, and in Developer ID mode `macos.notarize`. MyGo takes it as its project directory while `go` still builds this module, so binaries keep the exact source revision, unmodified. A new `mygo.json` key, or anything MyGo discovers next to its configuration (`package.json`, `frontend`, `locales`…), makes the launcher refuse until it is taught to carry it.
- No secret reaches CI, pull-request code, review, Pages, the draft smoke jobs, npm, pi or the app.

## Owner setup, once

1. In the Apple Developer account of the personal membership, check under **Membership details** that the program is active and note the **Team ID**.
2. Under **Certificates, Identifiers & Profiles**, create a **Developer ID Application** certificate (only the Account Holder can) or use the existing one, then export it with its private key from Keychain Access on the Mac as a `.p12` with a new password.
3. At account.apple.com › Sign-In and Security › App-Specific Passwords, make one named for example “yesman notarization”.
4. In GitHub, add the four secrets above. The `.p12` must be pasted as base64: on the Mac, `base64 -i <file>.p12 | pbcopy` copies it.
5. Commit the Team ID to `packaging/macos/signing.json` in a normal pull request, before the next release tag.
6. Delete the exported `.p12` file afterwards; the certificate itself stays in the login keychain.

The next release tag then builds signed. Setting the secrets without the Team ID, or the Team ID without the secrets, fails the release instead of signing ad hoc. Revoking the app-specific password or the certificate stops signing; clearing the Team ID **and** deleting all four secrets returns to ad hoc.

## Permissions across updates

macOS keeps some permissions, such as Accessibility and Screen Recording, against the app's code requirement. An ad-hoc build's requirement is its exact code hash, so a new build cannot satisfy the requirement saved for an old one. The first Developer ID release is therefore a one-time migration: the permissions granted to ad-hoc versions must be granted again. After that, releases from the same team and identifier share one designated requirement. That they keep permissions across a real update is to be shown by updating one signed build to another on a test Mac; requirement equality alone does not prove it. Renewing the certificate within the same team keeps the requirement; check it before switching.

## Local builds

Local and CI builds are ad hoc and need no flag:

```sh
CGO_ENABLED=1 CGO_CFLAGS='-O2 -g -mmacosx-version-min=13.0' MACOSX_DEPLOYMENT_TARGET=13.0 go tool mygo build
```

## Tests

`python3 scripts/test_macos_signing.py` (macOS) checks setup, cleanup and its ownership checks (forged, linked, copied or replaced directories and receipts are left alone, also when the directory is replaced after the last check; a FIFO receipt is refused without waiting; a signal or deadline during setup stops the tool's descendants and leaves nothing; a value alias or a failed output write fails setup cleanly; a keychain swapped in at the path during cleanup survives; when a tool's group cannot be confirmed stopped, setup keeps its files and cleanup removes them only once that group is empty), verification including weak requirements, the launcher's arguments, derived configuration, credential files and refusals with a stand-in `go`, that `TERM` stops the launcher's own process group but no other, that a group which cannot be confirmed stopped keeps the key and configuration until `--remove-retained` finds it empty, the draft gate's step script, and that the Apple secrets reach only the setup step. `--mygo` also runs the real MyGo build of a committed copy of the repository through the launcher, with stand-in Apple tools and `gh`: a plain `go tool mygo build` with no input; both architectures signed, notarized and stapled before the update archives, whose updater signatures verify; each failure stopping the build before any update file or upload; the binaries' exact, unmodified source revision; the same ad-hoc app, Linux and Windows files as the tracked configuration; and no credential name or value in the environment of `go` or any cgo compiler run. `--real-keychain`, only on a GitHub-hosted runner, has the real keychain tools refuse a synthetic self-signed “Developer ID Application” certificate and leave nothing behind. CI runs all three on both macOS architectures. None uses a real certificate or contacts Apple; a real signed release still has to be verified as described above.
