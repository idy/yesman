# Scheduled tasks

Tasks (定时任务) keep a yesman's scheduled tasks: requests the user saves for its lead, each due once, every day, every week or every few minutes, hours or days. They run while the app runs, in the tray too, and only then: yesman installs no system service, login item or timer, and asks for no permission. The code is [`internal/schedule`](../internal/schedule); the pane is [`web/schedules.js`](../web/schedules.js).

Saving a plan turned on is the user's authorization to send its request at its times, as if they typed it then: the lead handles it with the usual tools and rules, and must still ask before anything the user has not authorized. A plan holds natural-language instructions only; there is no scheduled shell command. Nothing creates plans by itself. The lead's `yesman_schedules` tool lists them and, only when the user asks for one, saves a draft that stays off until the user turns it on in Tasks. Workers have no access. A draft is saved only if, with the workspace held just before it is saved, the lead that asked still runs the process its credential was given to and belongs to the same workspace generation: a request whose body arrives after its lead was stopped, restarted or dismissed, or after a same-name workspace was hired, saves nothing.

## Where they are kept

| Path | What |
| --- | --- |
| `.yesman/schedules/plans.json` | Configuration: `version`, `next`, and each plan's `id` (`s1`, `s2`, …, never reused), `title` (≤120), `instructions` (≤4000), `schedule`, `timezone`, `enabled`, `revision`, `activeSince`, `createdAt`/`updatedAt`/`archivedAt`, `createdBy`. Fields it does not know are kept. A file it cannot read, or of a later version, is left unchanged: Tasks shows the error and runs nothing of it. |
| `.yesman/schedules/runs/<id>.json` | One record per run, missed range or skipped occurrence: plan, revision, kind, occurrence key and time, state, board task, submission attempts, last seen board outcome, and the title and instructions it sent. No transcript, images or secrets. |

At most 50 plans are on or off at once, 200 with archived ones: to make room, the oldest archived plan with no run still open is forgotten, its records removed only after the plans file was written. Each plan keeps its 30 newest finished records, and besides them every run still on its way or whose board task is open (or a board that cannot be read), however old; the record the schedule's cursor rests on also stays. A run whose delivery stayed unknown is kept while its board task is open; once the lead or the user marks it done or dropped, or removes it, it is history like any other. While a plan has 100 such open runs, Run now and catch-ups are refused and due occurrences are recorded as skipped, until some close. A view lists a plan's 60 newest records and counts the rest.

Every file is read only up to a size, and never written larger than it is read: what yesman saves always reads back. `plans.json` is read up to 6.3 MiB, room for 200 plans at their largest, with each character of a title or instructions written as six bytes (as JSON writes `<` or U+2028); a run record up to 64 KiB, about 40 KiB at its largest; `pruned.json` up to 1 MiB. A change that would make one larger, through fields this version does not know, say, is refused before anything is written, and the file stays as it was. A file found larger is shown as an error and left unchanged.

Every file is read, written and removed through handles opened from the store's folder of workspaces (`os.Root`), never by path: each folder on the way, the workspace itself, `.yesman`, `schedules` and `runs`, is checked to be a real folder, not a link, on the handle then used, before and after it is opened, and a file to be a regular file on the handle it is read from. A link anywhere on the way, pointing out of the store or into it, is refused and left as it is: Tasks shows why, the workspace's tasks do not run, and nothing is saved, until it is a folder again. A record replaced by a link reads as damaged and is never written through. Only the store's own folder is opened by its path, so it may be reached through a link the user chose (a moved data folder). The workspace opened must also be the one the operation started with: its `yesman.json` is read on the same handles, and a same-name workspace hired since gets nothing written.

A save replaces `plans.json` only if it is still the file read, with the same content: just before the new file takes its place, the file at its name is read again through the same folder and compared, by identity and content digest, with what yesman read or last wrote. A change made meanwhile on disk, edited in place, replaced, removed or created, is a conflict: the file stays as it was changed, the temporary file is removed, nothing yesman knows changes, Tasks says to reload, and the next read takes the file as it is now, so saving again keeps that change, fields this version does not know included. This covers the time from the read to the write; it is not a lock, and a writer outside yesman that changes the file in the instant between that last check and the replacement can still be overwritten.

What pruning removes still answers for itself. A missed record keeps the ID of its catch-up, so it is never caught up again after that run's record was pruned (and pruning writes it there first, if a crash kept it from being written). `schedules/pruned.json` keeps the request IDs of pruned manual runs, the 64 newest of each plan exactly and below them a floor: a request ID starts with the time the page made it (12 hex digits of milliseconds), and a click at or before the floor is refused as possibly made already, never sent as a new run. When `pruned.json` cannot be read it is left as it is, nothing is pruned, and Run now is refused with a notice in Tasks, while scheduled runs go on.

## When a plan is due

- **Once** at a date and time, **every day** at a time, **every week** on chosen days at a time: wall-clock times in the plan's own IANA time zone (`Asia/Shanghai`, `UTC`; never "Local"). The app embeds the time zone database, so Windows and Linux resolve the same names. Changing the computer's time zone does not move a plan.
- **Every N minutes, hours or days** (15 minutes to 7 days) is elapsed time from when the schedule was saved or turned on.
- Daylight saving time: a time that does not exist (clocks go forward) runs later by the gap, 02:30 becoming 03:30; a time that occurs twice (clocks go back) runs only the first time. A day with no such time at all is skipped. Each local occurrence has a key, its local date and time, and runs at most once.
- Saving or turning on a plan never runs times already past. A once plan saved on with its time past is refused; save it off and use Run now.

The scheduler wakes at the next due time or every 30 seconds and compares the wall clock. An occurrence seen within 10 minutes of its time runs (half the interval for shorter intervals). Times the app was closed, asleep or stalled for, or skipped by a clock jump, become **one missed record** with their count and range; they are never replayed by themselves. If the newest is still on time it runs and the older ones are missed. A missed record's **Run it now** catches up once, whichever and however often it is clicked. Setting the clock back never runs a recorded occurrence again: the plan waits until the clock passes its last recorded time.

While a plan's last run is still open, its delivery under way or its board task todo, doing or blocked, the next occurrence is **skipped** with a record naming that task, rather than piled on the lead. Run now is the user's explicit request and is allowed then, after a confirmation, unless the last run is still being sent.

## A run

1. **Claim.** Under the workspace's lock the plan is checked on and unchanged, then its record is created exclusively (`O_EXCL`). Two ticks, two schedulers or a repeated click produce one record. Turning the plan off before this prevents the run; after it, the run goes on and is shown — turning a plan off or archiving it never aborts the lead or touches its queue.
2. **Board task.** One task per run, linked by `schedule: {plan, run}`, which only the scheduler sets. Adding it is idempotent by run, so recovery never adds a second.
3. **Submission ID**, recorded before dispatch.
4. **Submit** through the agent manager's receipt path as a **follow-up**: an answering lead finishes first; it is never steered or aborted for a scheduled run. Its origin, `{source: "schedule", plan, run, submission}`, is kept in the receipt and, like every message's origin, decided from pi's own records of the prompt and kept beside the message (a custom entry pi never puts in a model's context); the window shows the message as the scheduled task's run, with **Open in Tasks**, never as something a person typed — also before pi took it, from its receipt. pi's command and the text are unchanged and carry no private IDs. The lead reads the plan's title and ID, its schedule, the planned time, its board task and the instructions. The run's own ID stays between the app and its window: the board that `yesman_board` returns to any agent, as text and as details, names a run's board task by its scheduled task (`schedule: {plan}`) only, field by field, so nothing else the board keeps reaches a model.
5. **Delivery state**, from pi's answer only: **sent** (accepted), **queued** (accepted into pi's follow-up queue), **not sent** (refused, or proven never to reach pi), or **unknown**. pi's acceptance (`ack`) stays recorded when the receipt later turns unconfirmed after a settle. A queued run whose lead process ended before reading it becomes unknown. Receipts are followed as pi reports them; a run still recorded as queued, or unknown, has its receipt read again once after the app opens (or takes the tasks over) and after an update was missed, a few at a time, without sending anything: a queue lost with a quit makes it unknown, and a receipt no longer kept leaves it unknown. An older copy of a receipt never replaces a newer one.

Each step is recorded before the next, inside the workspace's use lease, so a crash leaves a state the next start resumes or resolves:

| Left at | On the next start |
| --- | --- |
| claimed, board task maybe added | The board task is found by run, not added again; sent if still on time, else missed |
| submission ID recorded, no receipt | The ID is provably unregistered (newer than the receipt floor and retention): sent under it if still on time, else **not sent** with **Send again** |
| receipt exists (acknowledgment lost, quit mid-wait) | Resolved from the receipt; never sent again |
| receipt expired or evicted | **Unknown**, never sent again |

**Send again** is offered only when a run was definitely not delivered, and keeps its board task with a new submission ID. **Check again** rereads the receipt and sends nothing. **Run again as a new run** is the user's new intent: another run, board task and ID, after a warning that the lead may get it twice. Nothing is ever resent under a new ID by itself. This is at most one dispatch per submission ID and one run and board task per occurrence — not exactly-once execution across crashes, which no receipt can prove.

## What a run achieved

The result is the run's **board task**, which the lead and its workers keep with `yesman_board`: in progress, blocked, done or dropped, with its note. The run shows it, and keeps the last status and note if the task is later removed. Nothing is inferred from the lead's replies, a settled run or a worker finishing. The message asks the lead to mark the task with the outcome and to record the result in the task log (Working log) as usual; that is guidance, not something yesman enforces. The scheduler never writes the task log; its own facts are the run records in Tasks.

## Processes and lifecycle

One app per data directory runs the scheduled tasks: it holds an OS lock on `.runtime/schedules.lock`, which the system drops if the app ends. Another app shows them read-only and takes over when the lock is free; it carries on runs left under way, resolving them from their receipts. Without a lock no scheduler carries another's run. Dismissing a yesman retires its schedules before its workspace moves, and every write checks the workspace generation, so nothing reaches the archive or a new yesman with the same name. Quitting stops scheduling before the agents stop. The lock is let go once every delivery under way has ended, and not before, so that no other app takes over a run that may still go out: quitting waits two seconds for them, and when one still waits on pi, the lock goes as soon as it ends (or with the app).

## Editing and finding a plan in Tasks

The editor stays editable while a save is on its way, and what is typed meanwhile is not part of that save. When it is answered, the dialog stays open with what was typed, its caret and selection, on top of the version just saved: its revision, and the saved values in the fields not typed in. Saving again changes that plan, never a second one, and a change someone else made since is a conflict that keeps the text, not something saved over. A save answered after its dialog closed only refreshes the list; it moves neither the focus nor what Tasks shows.

A plan opened from its run's board task or from the conversation's **Open in Tasks** is found by its ID, in its own yesman, never by its title. An archived plan opens the Archived section on it and stays archived and off. A plan no longer kept, forgotten among the oldest archived ones, is said to be gone.
